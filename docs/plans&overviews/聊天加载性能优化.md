# 聊天加载性能优化

> 优化分支：`frontend-chatload`（已从 `frontend` 重命名，含全部优化提交）

---

## 1. 问题诊断

### 症状

- 长 session（500+ 条消息）切换时有明显卡顿，白屏数秒
- 同一 session 反复切换也卡顿——排除了网络原因
- 移动端 session 列表加载时无 loading 标识

### 根因分析

切换 session 走 `selectSession()` → `renderMessages(s.history)`，直接从内存 `modelData` 取数据，**不发起网络请求**。卡顿来自：

| 阶段 | 操作 | 耗时 |
|------|------|------|
| `renderMessages()` | 清空 `innerHTML`，遍历全部 history 做 tool 分组 | O(n) |
| `_renderMsgEl()` 逐条 | `marked.parse()` Markdown 解析 | **每条 5-50ms** |
| 同上 | `katex.renderToString()` LaTeX 渲染 | 每条 5-20ms |
| 同上 | `hljs.highlightElement()` 代码高亮 | DOM 操作 |
| 同上 | `el.scrollTop = el.scrollHeight` | **每 append 一次就触发 reflow** |
| 同上 | `el.appendChild(div)` 逐条插入 DOM | 逐个触发重排 |
| API | `/api/sessions` 返回**全部 session 的全部 history** | 网络传输大 |

**N 条消息 = N 次 marked + N 次 scrollTop reflow + N 次 DOM append = 数秒阻塞。**

---

## 2. 优化方案（6 个方向）

### 2.1 去掉逐条 scrollTop + 批量 DOM 插入

**状态**：已实现 ✓

**改动**：`ts/app.ts`

- `_renderMsgEl` / `_renderToolGroup` 移除 `el.scrollTop = el.scrollHeight`
- `renderMessages()` 用 `DocumentFragment` 批量收集所有元素，一次 `appendChild`
- 只在最后设置一次 `el.scrollTop`
- 流式路径（`addMessage`、`appendEvent`）添加 `scrollMessages()` helper 保持逐条自动滚动

**效果**：1000 条消息从 N 次 reflow → 1 次。

### 2.2 Markdown 渲染缓存

**状态**：已实现 ✓

**改动**：`ts/app.ts`

- 模块级 `Map<string, string>` 缓存（LRU，上限 2000 条）
- `renderMarkdown()` 先查缓存，命中直接返回
- 缓存 key = 原始文本 content，value = 渲染后 HTML

**效果**：切换回已浏览 session 时 `marked.parse()` + `katex` 全走缓存命中，~0.01ms/条。首次渲染仍需解析，但后续切换近乎瞬时。

### 2.3 分片渲染

**状态**：已实现 ✓

**改动**：`ts/app.ts`

- `RENDER_CHUNK = 30`：每批渲染 30 个消息节点
- 首片同步渲染（立即可见），剩余通过 `setTimeout(renderNextChunk, 0)` 让出主线程
- `_renderVersion` 版本号机制：切换 session 时旧分片自动取消

**效果**：长 session 首次加载不阻塞 UI，消息逐批出现，用户可立即交互。

### 2.4 服务端分页 + 懒加载

**状态**：已实现 ✓

**改动**：`src/server.py` + `ts/app.ts`

- `/api/sessions` 只返回最后 `HISTORY_TRUNCATE = 50` 条消息，设 `historyTruncated: true`
- 新增 `GET /api/sessions/{id}/history?before=<index>&limit=50` 分页端点
- 前端 `selectSession()` 检测 truncated → `loadOlderMessages()`
- `#messages` 滚动到顶部 200px 内自动触发加载更早消息
- `loadOlderMessages` 用 `getBoundingClientRect` 锚定参考元素，prepend 后还原滚动位置

**效果**：网络传输从全量历史 → 50 条摘要，大幅减少初始加载和 WebSocket 事件触发的数据传输量。

### 2.5 窗口化渲染（含 spacer 占位）

**状态**：已实现，但实际效果差 ✓✗

**改动**：`ts/app.ts`（Commit `b90efe2` → 被 `60485b7` 修复部分）

- `MAX_MESSAGE_NODES = 500`：DOM 中最多保留 500 个消息节点
- spacer 占位 div（top/bottom），裁剪远端消息时保留高度
- `trimExcess('top')` / `trimExcess('bottom')` 在流式输出和加载历史时裁剪
- 裁剪时用 `offsetHeight` 实测高度维护 spacer

**问题**：
- spacer 系统增加大量 querySelector + reflow 开销，反而拖慢流程
- 流式输出中每 append 一条消息就调用 trimExcess，产生不必要开销
- 容易出现空白屏幕（spacer 高度追踪错位）

**最终修复**（Commit `60485b7`）：
- 删除全部 spacer 系统（`ensureSpacers`、`trimMessagesTop/Bottom`、`trimExcess`、`_msgNodeCount`，共 ~80 行）
- 删除流式路径中的 trimExcess 调用
- 只在 `loadOlderMessages` 中保留简单裁剪：`MAX_MESSAGE_NODES = 2000`，超出时直接 `removeChild(lastElementChild)` 移除底部节点，不维护 spacer

### 2.6 虚拟滚动

**状态**：未实现（建议未来探索）

**思路**：只渲染可视区域 + 上下 buffer 的 DOM 节点，滚动超出视口的消息销毁并用占位 div 保持滚动位置。

**理由未做**：markdown 渲染消息高度不可预测，spacer 高度估算复杂；当前 DocumentFragment + 缓存 + 分片已能满足 2000 条以内的流畅体验。

## 5. 经验教训

1. **先分析再动手**：通过逐层 trace `selectSession → renderMessages → _renderMsgEl → renderMarkdown` 精准定位瓶颈在 marked/mathjax 的 CPU 密集渲染和逐条 reflow，而非网络传输。

2. **DocumentFragment 是低垂果实**：一行 `createDocumentFragment` + 批量 `appendChild`，没有副作用，大幅减少 reflow。

3. **缓存策略要配尺寸限制**：Markdown 缓存不加限制会无限增长。LRU + 2000 条上限在内存安全的同时覆盖了大部分回访场景。

4. **setTimeout(0) 分片比 requestIdleCallback 更可控**：requestIdleCallback 在低优先级时可能延迟很久，setTimeout 0 保证在下一个 event loop 执行，又能让出主线程给用户交互。

5. **spacer 虚拟滚动不要用 offsetHeight 追踪**：会导致频繁 reflow，反而比直接渲染更慢。真要做虚拟滚动需要用 ResizeObserver 或估算高度。

6. **流式路径不要加 trim**：流式输出时每 append 一条就跑 trim 是纯开销。只在批量加载时（loadOlderMessages、renderMessages 完成）做一次性裁剪。

7. **优化要有节制**：窗口化渲染/spacer 系统增加了 ~80 行复杂代码，实际效果反而不如不做。始终以实测为准，不要过度设计。
