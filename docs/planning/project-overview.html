Agent 集群操控系统

主 Agent 操控多个 CLI 子 Agent 并行协作 · 方案探索中 Phase 0-1 完成 · 最后更新 2026-06-12

项目概览

一句话

用一个 AI（主 Agent）调度管理多个 AI CLI（CodeBuddy Code、Copilot CLI 等），让它们像团队一样分工协作。

架构（三句话） 
用户 → 消息网关 → 主 Agent → 调度器 → 适配器 → CLI 进程
  1. 消息网关 — 统一多入口（CLI/Web/QQ），归一化为标准消息
  2. 主 Agent + 调度器 — 拆分任务，分发到子 Agent
  3. 适配器 + 进程管理 — 每种 CLI 一个适配器，用 OS 进程原语统一控制
关键技术决策
决策方案淘汰的方案
多轮对话spawn 独立进程 + stream-json + --resume--bg 管道多轮（失败）
进程管理OS 原语 (PID/kill/wait)依赖 CLI 自身 ps/logs（不可移植）
跨 CLI 兼容适配器模式，差异仅命令行参数—
Session 管理自定义 sessions.json + PIDCLI 自带 session 管理（不统一）
记忆隔离子 Agent 独立 workdir共享目录 MEMORY.md（会泄露）
Windows 操控node-pty (bash 包装)tmux（Windows 不可用）

Phase 1

已完成（16 项实验）

目标：持久化 Session 操控

找到一种可靠方式，让主 Agent 能对子 CLI（CodeBuddy Code / Copilot CLI 等）进行多轮对话操控。 核心约束：子 CLI 会话必须支持长对话上下文保持，不能每次重新开始。

首选方案：Shell / child_process 通用进程控制（方案D）

思路

上移一层到 OS 级别：不依赖 CLI 自己的 --bg/ps/logs，用操作系统原语（PID、信号、重定向）统一管理所有 CLI 进程。这是经过 A/B/C 三轮探索后验证的可行路径。

PID 追踪✅✅s5
多 Worker 并行✅✅s5
--resume 上下文✅✅s3

核心代码（完整版见 shell-process-control.md）：

import { spawn } from 'child_process';

class ProcessManager {
  spawn(name, cmd, args): string {
    const child = spawn(cmd, args);
    const id = `${name}-${Date.now()}`;
    this.workers.set(id, { pid: child.pid, process: child });
    child.on('exit', code => this.onExit(id, code));
    return id;
  }
  isAlive(id): boolean {
    try { process.kill(this.workers.get(id).pid, 0); return true; }
    catch { return false; }
  }
  kill(id): void { this.workers.get(id)?.process.kill(); }
}

CLI 差异与调度注意事项

不同 CLI 在 session 管理、工作目录隔离、生命周期等方面存在显著差异。调度器和适配器必须考虑这些差异，不能假设所有 CLI 行为一致。

已确认的 CLI 差异（CBC）

维度CodeBuddy Code (cbc)备注
跨目录 Session 切换 ❌ 不支持 --resume 需与 --cwd 保持一致，session 绑定创建时的工作目录
长闲置 Session 保留 ❌ 不可永久保留 长期不活跃的 session 可能被自动清理/过期
Session 删除 ❌ 无原生删除 无法通过 CLI 接口清理已结束的 session
Session 列表查询 有限 调度器不能依赖 CLI 自带的 session list 做管理
后台进程管理 有 --bg（已弃用） 统一用 OS 原生进程管理替代

对调度器的影响

1. Session 与工作目录绑定

调度器在 spawn 阶段确定 workdir 后，该 session 的后续 continue 调用必须用同一 workdir。调度器需要为每个 session 持久化记录 { sessionId, workdir } 映射。

2. Session 生命周期与归档策略

核心思路：不与 CLI 的 session 回收机制对抗，而是由主 Agent 统一接管 session 管理。

三类 session，三种策略

类型策略由谁负责
活跃 session
当前正在执行任务或刚完成		 心跳保活，保持 --resume 可用 调度器
无价值 session
一次性任务，用完即弃		 不做额外处理，让 CBC 自己 GC CBC（免费）
有价值 session
需长期保留上下文的任务		 由主 Agent 显式标记后归档，过期后可重建 主 Agent + 调度器

归档内容（短期 + 长期）

数据类型短期意义长期意义存储方式
Session 元数据
sessionId、CLI 类型、workdir、用途标签、摘要		 高 快速索引/查询 中 — 不同 CLI 格式不同，难以统一 sessions.json
完整对话历史
messages[] 数组，与 CLI 无关的通用格式		 低 高 跨 CLI 通用，未来可能抛弃元数据 archive/{sessionId}.json
决策：当前阶段元数据 + 对话历史都存。 短期依靠元数据做快速查询，长期依靠对话历史实现跨 CLI session 迁移。

归档触发条件

  • 显式标记 — 主 Agent 调用 markValuable(sessionId)（非调度器启发式判断）
  • 过期监听 — 检测到 --resume 返回 session-not-found，若已标记为有价值则自动触发重建

重建流程

  1. 从 archive/{sessionId}.json 读取完整对话历史
  2. 新 spawn 一个子 CLI 进程
  3. 将历史作为 conversationSeed 注入（适配器负责序列化为对应 CLI 的格式）
3. Session 清理（OS 层完成）
  • kill(pid) 终止进程
  • 从 sessions.json 移除记录
  • 清理 workdir 中的临时文件
4. 适配器能力矩阵（CLIIdentity 接口） 
interface CLIIdentity {
  name: string
  capabilities: {
    crossDirResume: boolean    // --resume 是否跨目录有效
    sessionTTL: number | null  // session 过期时间（毫秒），null 表示永久
    nativeSessionDelete: boolean // 是否有原生 session 删除
    nativeSessionList: boolean // 是否有原生 session 列表
  }
}

每个 CLI 适配器必须明确声明自身能力矩阵，调度器据此决定策略。

5. 本地提示词约束

向子 CLI 发送 prompt 时，应附带 CLI 特性约束提示（如告知子 Agent 它的 session 有有效期，需及时返回结果，避免长时间思考导致 session 断开）。

后续验证项

  • CBC session 实际过期时间 — 策略已定，不测精确 TTL，走归档+重建
  • 其他 CLI 的 session 行为？ — Claude Code / Aider 等接入时补充
