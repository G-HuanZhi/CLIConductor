# CLIConductor 修复与 Adapter 抽象实施计划

**制定日期**: 2026-07-01
**配套文档**: [code-review-2026-07-01.md](./code-review-2026-07-01.md)
**目标**: 在引入多 CLI adapter 之前，先把现有代码收敛到可抽象的状态，再分阶段实施

---

## 总体策略

### 核心原则

> **抽象层应该建在已经收敛的代码上，而不是用来"统一"已经发散的代码。**

当前 `worker.py` 有 3 处独立 spawn 路径（`create_worker` / `branch_worker` / `_spawn_process`），参数构造各不相同、`--model` 默认值还不一致。如果在外部还没统一的情况下抽象 adapter，等于把 3 套不一致 × N 个 adapter = 3N 套不一致。

### 模型选择策略

| 任务类型 | 推荐模型 | 理由 |
|---|---|---|
| 按报告修 bug / 抽函数 / 改 import | DeepSeek-V4-Pro | 机械任务，无需 GLM 的推理能力 |
| 性能优化（save 异步化、list_all 缓存化） | DeepSeek-V4-Pro | 模式清晰，按图施工 |
| adapter 接口设计的关键决策 | GLM-5.2 | 需要架构判断 |
| 疑难 bug 深度推理（如 `_replaying` 竞态） | GLM-5.2 | 需要深度分析 |
| 第二个 adapter 实现 | DeepSeek-V4-Pro | 已有范式，机械复制 |

**成本估算**：GLM 单价约为 DS 的 4 倍。按上述分工，GLM 只用于"真正需要判断"的 10-20% 工作量，整体成本约为纯 GLM 方案的 30%。

## 阶段 1：Adapter 抽象的前置清理

**目标**：把 `worker.py` 的 spawn 路径收敛成单一入口，Session 字段处理收敛成单一函数。
**模型**：DeepSeek-V4-Pro
**预计工作量**：5 项，每项 10-30 分钟

### 1.1 修复 `_spawn_process` 与 `create_worker` 的 `--model` 不一致

**问题位置**: `src/worker.py:296` vs `src/worker.py:446-447`

**当前代码**:
```python
# create_worker (line 296) — 总是传 --model
extra_args = ["--model", s.model or DEFAULT_MODEL]

# _spawn_process (line 446-447) — 仅当 s.model 真值时才传
if s.model:
    args.extend(["--model", s.model])
```

**后果**: `restart_worker` / `respawn_worker` 走 `_spawn_process`，若 `session.model` 为 None/空字符串，重启后 cbc 会用它自己的默认模型，与首次 spawn 的模型不一致。

**修复思路**:
- 统一为 `args.extend(["--model", s.model or DEFAULT_MODEL])`
- 在 `_spawn_process` 里改这一行即可
- 验证：写一个 test，session.model=None 时 restart 后 spawn_args 包含 `--model <DEFAULT_MODEL>`

**验证命令**:
```bash
python tests/test_worker_history.py
```

### 1.2 让 `create_worker` / `branch_worker` 复用 `_spawn_process`

**问题位置**: `src/worker.py:275-337` (`create_worker`) 和 `src/worker.py:559-622` (`branch_worker`)

**当前状态**: 两个函数都手搓 `--model --permission-mode --effort --thinking --resume` 等参数，而 `_spawn_process` 已经封装了同样的逻辑（且行为还不一致，见 1.1）。

**修复思路**:
- `create_worker` 改为调用 `_spawn_process(session_id)`，不再自己拼参数
- `branch_worker` 需要额外传 `--fork-session`，改为 `_spawn_process(session_id, extra_args=["--fork-session", ...])`
- 注意：`branch_worker` 当前还手搓了 `--resume s.cbc_session_id or ""`，需要确认 `_spawn_process` 的 `--resume` 逻辑能处理空字符串情况（可能需要在 `_spawn_process` 里加判断：只有 `s.cbc_session_id` 非空才传 `--resume`）
- 删除 `create_worker` 和 `branch_worker` 里的参数拼装代码

**风险点**:
- `branch_worker` 的 `--fork-session` 是 cbc 特有参数，未来 adapter 抽象时这个参数应该由 adapter 提供
- `_spawn_process` 当前对 `extra_args` 的处理是 `args.extend(extra_args)`，会附加在后面，可能与前面的 `--model` 冲突（cbc 一般以后面的为准，但需验证）

**验证**: 手动测试 branch 功能 + 跑现有测试

### 1.3 抽取 Session 字段提取/更新的公共函数

**问题位置**: 3 处重复
- `src/server.py:269-297` (`api_create_session`)
- `src/server.py:381-402` (`api_spawn` 新 session 分支)
- `src/server.py:209-237` (`ws_agent_endpoint` spawn 分支)

以及 4 处字段更新逻辑：
- `src/server.py:314-323` (`api_update_session`)
- `src/server.py:370-380` (`api_spawn` 已有 session 分支)
- `src/server.py:541-549` (`api_worker_settings`)
- `src/server.py:622-628` (deprecated `switch-thinking`)

**修复思路**:

在 `src/server.py` 顶部（或新建 `src/server_helpers.py`）加两个函数：

```python
def _build_session_params(data: dict) -> dict:
    """从请求 data 提取 session 创建参数，统一默认值。"""
    name = data.get("name", "default")
    return {
        "name": name,
        "model": data.get("model") or worker.DEFAULT_MODEL,
        "permission_mode": data.get("permissionMode") or None,
        "always_thinking_enabled": data.get("alwaysThinkingEnabled", False),
        "effort": data.get("effort", ""),
        "max_thinking_tokens": data.get("maxThinkingTokens", 16000),
        "workdir_name": data.get("workdir") or name,
    }

def _apply_session_updates(s: sess.Session, data: dict) -> bool:
    """把 data 里的字段应用到 session，返回是否有变更。"""
    changed = False
    if "model" in data:
        s.model = data["model"]
        changed = True
    if "permissionMode" in data:
        s.permission_mode = data["permissionMode"] or None
        changed = True
    if "alwaysThinkingEnabled" in data:
        s.always_thinking_enabled = data["alwaysThinkingEnabled"]
        changed = True
    if "effort" in data:
        s.effort = data["effort"]
        changed = True
    if "maxThinkingTokens" in data:
        s.max_thinking_tokens = data["maxThinkingTokens"]
        changed = True
    return changed
```

然后 7 处调用点全部改为调用这两个函数。workdir 创建逻辑也可以抽出来：

```python
def _resolve_workdir(workdir_name: str) -> Path:
    """返回 WORKDIRS_DIR / workdir_name，并确保目录存在。"""
    workdir = WORKDIRS_DIR / workdir_name
    workdir.mkdir(parents=True, exist_ok=True)
    return workdir
```

## 阶段 2：Adapter 抽象

**目标**：把 cbc 特有的逻辑从 `worker.py` 抽离到 `CbcAdapter`，定义 `Adapter` 协议。
**模型**：GLM-5.2（接口设计）+ DeepSeek-V4-Pro（实现）
**预计工作量**：1-2 个工作单元

### 2.1 定义 Adapter 协议

**位置**: 新建 `src/adapters/__init__.py` 或 `src/adapter.py`

**协议设计草案**:

```python
from __future__ import annotations
from typing import Protocol, AsyncIterator
from src.session import Session


class CliAdapter(Protocol):
    """CLI 工具适配器协议。

    每种 CLI 工具（cbc / claude-cli / gemini-cli / ...）实现此协议，
    worker.py 通过协议接口调用，不感知具体工具。
    """

    @property
    def name(self) -> str:
        """适配器名称，如 'cbc' / 'claude'。"""
        ...

    def base_args(self) -> list[str]:
        """启动 CLI 进程的基础参数（不含 model/thinking 等）。"""
        ...

    def model_args(self, s: Session) -> list[str]:
        """返回 --model 参数。"""
        ...

    def thinking_args(self, s: Session) -> list[str]:
        """返回思考模式相关参数。"""
        ...

    def effort_args(self, s: Session) -> list[str]:
        """返回 effort 级别参数。"""
        ...

    def resume_args(self, s: Session) -> list[str]:
        """返回 --resume 参数（用于恢复会话）。"""
        ...

    def fork_args(self, s: Session) -> list[str]:
        """返回 fork 会话参数。"""
        ...

    def build_spawn_args(self, s: Session, extra: list[str] | None = None) -> list[str]:
        """组装完整的 spawn 参数列表。"""
        ...

    def encode_user_message(self, text: str) -> bytes:
        """把用户文本编码成 CLI 进程 stdin 接受的字节流。"""
        ...

    def parse_event(self, line: str) -> dict | None:
        """解析 CLI stdout 的一行，返回事件 dict 或 None（无法解析时）。"""
        ...

    def extract_cbc_session_id(self, event: dict) -> str | None:
        """从 init 事件中提取会话 ID。"""
        ...

    def extract_assistant_blocks(self, event: dict) -> list[dict]:
        """从 assistant 事件中提取 text/thinking/tool_use 块。
        返回格式: [{"role": "assistant"|"thinking"|"tool", "content": str}, ...]
        """
        ...

    def extract_result_text(self, event: dict) -> str | None:
        """从 result 事件中提取最终文本。"""
        ...
```

**设计决策点**（需要 GLM 判断）:
- 协议用 `Protocol`（结构化子类型）还是 ABC（名义子类型）？建议 `Protocol`，更灵活
- `build_spawn_args` 是协议方法还是由 worker.py 拼装？建议协议方法，让 adapter 自己决定参数顺序
- `parse_event` 返回 dict 还是自定义 Event 类型？初期 dict，后续可演进
- 是否需要 `validate_model(model) -> bool` 方法？

#### 3.2.3 `_replaying` 竞态（审查报告 1.4）
**位置**: `src/worker.py:222-223`

**这是疑难项，建议 GLM-5.2 处理**。

**问题**: user 消息清除 `_replaying` 后，cbc 仍可能吐出残留的 replay 旧 assistant 事件，被当成新消息 append。

**修复思路**:
- 引入 `replay_generation: int`，user 消息 ++generation
- replay 期间记录 `replay_done_generation = current_generation`
- assistant 事件 append 时，若 `event.generation <= replay_done_generation` 则跳过
- 但这需要 cbc 配合在事件里带 generation，不一定可行

**备选思路**:
- 用时间戳窗口：replay 期间的事件通常在 spawn 后 N 秒内到达，user 消息后的 2 秒内若收到 assistant 事件且内容与 history 最后一项重复，则跳过
- 启发式，不完美但能挡住大多数情况

**建议**: 先记录为 known issue，等第二个 adapter 实现后再统一解决（不同 CLI 的 replay 行为可能不同）。

#### 3.5.3 WS 在线时停轮询

## 风险与回滚

### 风险点

1. **阶段 1.2 改 spawn 路径**: `branch_worker` 的 `--fork-session` 参数顺序可能影响 cbc 行为
   - 缓解: 改完手动测试 branch，对比改前后的 spawn 命令行
2. **阶段 2 adapter 抽象**: 协议设计不当可能导致后续 adapter 实现困难
   - 缓解: 用 GLM 设计协议，且先实现 CbcAdapter 验证，不要急着加第二个 adapter
3. **阶段 3.3.1 save 异步化**: 异步写盘可能引入新的竞态（save 期间 session 被改）
   - 缓解: 异步化时对 to_dict() 做快照，快照后再 to_thread
4. **阶段 3.3.5 QQ Bridge WS 订阅**: WS 断线重连逻辑复杂
   - 缓解: 保留轮询作为 fallback，WS 在线时停轮询，断开时恢复

### 回滚策略

- 每个阶段独立 commit，回滚到上一阶段即可
- 阶段 1 和阶段 3 各项相互独立，可单独回滚
- 阶段 2 是大改动，建议在独立分支上做，验证通过后合并
